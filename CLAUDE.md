# BArch: agent guide

This repository is Bruno's whole Arch Linux desktop. Everything here is live: the usual paths
(`~/.config/hypr`, `~/.config/quickshell`, ...) are symlinks into this repo, so an edit here
changes the running system immediately. Talk to Bruno in Brazilian Portuguese; code, comments
and commit messages stay in English, like the rest of the repo.

@README.md

## Hard rules

- **Never run anything with sudo yourself.** When a step needs root (`/etc`, `/boot`,
  `/usr/local/bin`, pacman), show the exact command and let Bruno run it.
- **Never update the system by hand** (`pacman -Syu`, `paru -Syu`, `claude update`). Updates only
  happen through the bar's Update All (`run-update.sh`, under `quickshell/`).
  Installing a single new package with `paru -S` is fine once Bruno agrees.
- **Kernel:** `linux-cachyos` is built by `bin/.local/bin/kernel-update` and is in `IgnorePkg`.
  Do not install, remove or rebuild kernels, and do not touch the UKI, Limine, Secure Boot
  (sbctl), LUKS, TPM enrolment or `/etc/kernel/cmdline` unless Bruno asks for that specifically.
- **Saving = `./scripts/sync.sh "message"`**, never `git commit`/`git push` directly. It refreshes
  the package lists and the `system/` snapshot, scans for secrets, commits and pushes. Do not run
  it without Bruno's go-ahead (it asks for his sudo password).
- **No secrets in the repo.** App passwords (vdirsyncer, etc.) stay outside. Never add
  `~/.claude` contents other than `settings.json`, `CLAUDE.md` and skills that live in this repo.

## Controlling the desktop: `barch`

Prefer `barch` (`bin/.local/bin/barch`, see `barch help`) over editing state files, calling
`hyprctl`/`gsettings` or `notify-send` whenever a subcommand exists: notifications, theme, HDR and
SDR brightness, side monitor, caffeine, night light, Do Not Disturb, system health, agent tasks,
AUR review, safety snapshots, voice control (`barch voice`). Use `--json` to
read state and check the exit code (`3` = the bar is not running). A new bar feature that scripts
should reach gets an `IpcHandler` function answering JSON (`{"ok": ...}`) plus a `barch` subcommand,
reusing the widget's own functions.

## Agent infrastructure

- **Safety snapshot:** sessions started in `~/BArch` get a snapper pre/post pair of `/` (the
  SessionStart hook tells you the pre number). If the hook reports that the snapshot failed, say
  so before touching anything outside the repo.
- **Failures:** `barch failure` saves logs to `~/.local/state/barch/failures/`. A session opened
  from **Investigate** starts with one of those logs: diagnose, then propose the fix and wait.
- **Scheduled tasks** live in `agent/tasks/`: `<task>.md` (frontmatter `description`, `tools`,
  `notify: always|issues|never`, optional `model`; the body is the prompt), an optional
  `<task>.sh` (`prepare <rundir>` writes `context.md`, exit 75 = nothing to do; `finish <rundir>
  <result.json> <report>`), an optional `<task>.schema.json`, and a timer
  `systemd/.config/systemd/user/barch-agent@<task>.timer` listed in `packages/user-services.txt`.
  Tasks are read-only (`dontAsk` + an allow list): gather facts in the `.sh`, not by widening
  `tools`. Reports: `barch agent report <task>`.
- **Reactive rules and metrics:** `agent/events.py` (`barch-events.service`) samples the machine
  into `~/.local/state/barch/metrics.db`, turns Hyprland/VPN/network/AirPods/lock/failure changes
  into events and runs `agent/rules.json` (`barch rules|events|metrics`, README "Automation").
  A new automatic reaction is a rule there, not a new timer or script; a new source of events or
  metrics is a sampler in `events.py` (and its name in the `_doc` of `rules.json`).

## How the repo works

- **Stow packages** are the top-level folders listed in `PACKAGES` in `scripts/lib.sh`
  (`[name]="paths it owns under $HOME"`). A new package needs an entry there, or a fresh install
  will not link it. List file paths (not the parent folder) when the target folder also holds
  local state, as `claude` does with `.claude/settings.json`.
- **`system/`** is a *copy* of files from `/etc`, `/boot` and `/usr/local/bin` (list in
  `SYSTEM_FILES`), collected by `scripts/collect-system.sh` and restored by
  `scripts/apply-system.sh`. Editing `system/files/...` does nothing to the live system: change
  the real file (Bruno, with sudo), then `sync.sh` collects it.
- **Packages:** `packages/pacman.txt` and `aur.txt` are regenerated by `sync.sh`; edit
  `aur-ignore.txt` to exclude something. User services go in `packages/user-services.txt`.
- **Hyprland config is Lua** (0.57, `hl.*` API, stubs in `/usr/share/hypr/stubs/hl.meta.lua`).
  There is no `hyprctl keyword`: live changes go through `hyprctl eval` + `hl.config{}`. The
  Hyprland Settings app (`quickshell/hypr/`, `barch hypr`) never edits `conf/*.lua`: it writes
  `hypr/.config/hypr/settings.json`, applied by `conf/settings.lua` on top of the files
  (`BArch.settings.apply`). To change an option for Bruno, prefer `barch hypr set <opt> <value>`
  over editing the Lua by hand when it is a one-off; hand-written files stay the base.
- **Apps with their own window** (`quickshell/hypr`, `center`, `backup`, `packages`, `mixer`,
  `music`, `palette`) run as `qs -p <dir>` and cannot import outside their folder: the shared controls live
  in `quickshell/ui/` and are symlinked into each app (`ln -s ../ui/X.qml`), and every component
  must be listed in the app's `qmldir`. Closing the window quits the process; `barch hypr|center|
  packages|mixer`, `barch backup browse`, `barch music browse` start a new one. In their shell commands resolve the repo
  with `readlink -f` (`Quickshell.shellDir/../../../..` only works physically, the shell dir is a
  symlink). `hypridle.conf` and `hyprsunset.conf` are edited by the Hyprland app's Idle and Night
  light pages (hyprlang parser in `hypr/hypr.js`, comments kept).
- **Voice control** (`quickshell/voice/`): `voice.py` is the daemon, `commands.json` the intents in
  Portuguese (regex on normalized text: lower case, no accents); `languages.json` the other languages
  it can listen in (`barch voice lang`), which skip the table and go straight to Claude. Test a sentence with
  `barch voice match "..."` (prints what would run, runs nothing); `barch voice test "..."` runs it
  for real on the live desktop, so never use it on a list of examples.
- **Music pipeline** (`server/music/`): runs on the NAS in its own container (`barch-music`), not on this machine;
  `barch music install` copies it there. The naming rules are in `style.py` and were measured over
  the whole library: change them only with `tests/test_style.py` passing. Never write to `/music`
  from here (the share is read only for this user); fixes go through scripts run in the container.
- **Video** (`server/video/`): Recyclarr keeps Radarr/Sonarr's "BArch 4K" profile (2160p HEVC HDR,
  one quality step, 250 MB/min cap, PT-BR preferred) and the PT-BR pipeline (`barch-video` container,
  `barch video`) muxes a dub from another release into each 4K file. Change `sync.py` only with
  `tests/` passing and a real pair checked (`python3 -m barch_video mux` in the container writes a
  `.barch.mkv` next to the reference, nothing replaced). Never delete movie files with Radarr's
  `moviefile/bulk` (6.4 leaves them on disk); one by one, and check the disk.
- **NAS kernel module** (`server/unraid/`): the `i2c-nct6793` build script for OpenRGB on the NAS
  (README "NAS"). It runs on the NAS, never here; the package is per Unraid kernel.
- **Theme:** `quickshell/.config/quickshell/theme/palettes.json` holds the palettes (ten tones
  each) and `theme/Theme.qml` derives everything else from them. Change colors there (or with
  `barch theme edit`), never in the generated files (they are git-ignored and get overwritten).
  The bar is the only writer of `palettes.json` (`theme save`/`remove` over IPC).
- **Fresh install / VM:** `install.sh` + `scripts/apply-system.sh` must keep working on a clean
  Arch and inside a KVM VM (they detect a VM and skip NVIDIA, the CachyOS kernel and disk/boot
  files). Any new dependency goes into the package lists; any new user service into
  `user-services.txt`.

## Verifying a change

- Hyprland: `hyprctl reload`, then `hyprctl configerrors` must be empty. Live values:
  `hyprctl -j monitors`, `hyprctl binds -j`, `hyprctl eval '...'` (e.g. `BArch.monitors`).
- Quickshell reloads QML on save; check its log for errors after every QML change.
- Shell scripts: `bash -n` and, if installed, `shellcheck`. `./scripts/check.sh` runs every static
  check of the repo at once (scripts, Lua, JSON, user units, agent timers, `hyprctl configerrors`);
  `sync.sh` runs it before committing.
- Keybindings: a new bind needs a `"Group|Description"` in `binds.lua` so it shows in the
  shortcut sheet (Super+/); group `Hidden` keeps it out.
- When a user-visible feature changes, update `README.md` in the same change.
- Lock screen: look at it only through `quickshell/lock/preview.sh` (own Shell ID). Never start,
  kill or reload the real lock (`lock/shell.qml`): it is a resident process and may be what is
  holding the session. It does not watch files, so an edit under `lock/` only applies after
  `hypr/scripts/lock.sh --relaunch`, which Bruno runs (safe while unlocked).

## Machine

Ryzen + 64 GB RAM, NVIDIA RTX 4080 (`nvidia-open-dkms`), Alienware AW3225QF (4K QD-OLED, HDR,
DisplayPort) plus a side monitor, btrfs on LUKS2 with Snapper (`snap-pac`), zram, PipeWire,
Hyprland under uwsm with autologin on tty1 and the Quickshell lock screen (`quickshell/lock/`) at
session start (no other locker: `hypr/scripts/lock.sh` starts the resident lock process, tells it
to lock and restarts it if it dies).
